## 3줄 요약

- 배경: 제안서는 "질문을 쓰는 압축(LongLLMLingua)이 일반 요약보다 판단을 더 잘 보존하는가"를 한 번에 비교하려 했습니다.
- 개선: 새 설계는 비교를 단계별로 쪼갰습니다. 먼저 질문 없는 압축끼리 비교하고, 질문 효과는 추가 분석에서 따로 봅니다.
- 핵심: 한 번에 하나만 바꿉니다(변인통제). 그래야 결과가 달라졌을 때 이유를 설명할 수 있습니다.

## 1. 기존 설계(제안서)의 한계

**제안서가 스스로 적은 한계 (6쪽)**

1. 목표 토큰 수와 실제 출력 길이가 다를 수 있음
2. 방법마다 질문 사용 여부가 달라 알고리즘 효과만 분리하기 어려움
3. 조건·예외가 삭제되거나 문장이 변형되면 의미 보존 판단이 어려움
4. 질문별 압축은 비용이 들고, 결과를 다른 문서로 일반화하기 어려움

**추가로 보완이 필요했던 점** (제안서가 7장이라 생략됐을 수 있음. 문서에 없다는 사실만 확인했습니다)

- 공식 123문서(2,091문제)를 그대로 사용하며 중복·라벨 충돌 계약서 점검 절차가 없음
- 같은 계약서의 17문제는 서로 독립이 아닌데 이를 반영한 통계 처리가 없음
- 모델이 라벨 형식에 맞지 않게 답했을 때의 처리 규칙이 없음
- Dev/Test 사용 규칙이 명시되지 않아 Test를 보며 설정을 고를 위험이 있음

## 2. 핵심 변경: 조건을 2×2로 분리

|                 | 보존 우선 지시 없음    | 보존 우선 지시 있음                |
| --------------- | -------------- | -------------------------- |
| 생성형 (새로 쓰기)     | 생성형·일반 (Naive) | 생성형·보존 우선 (Contextualized) |
| 추출형 (원문 문장 고르기) | 추출형·일반         | 추출형·보존 우선                  |

- 같은 줄 안에서는 "보존 우선 지시 문장 하나"만 다릅니다.
- 같은 칸 안에서는 "출력 방식"만 다릅니다.
- Original(원문 그대로)은 기준선으로 함께 평가합니다.
- 기존에는 Naive, Contextualized, LongLLMLingua가 쓰는 방식, 지시 내용, 질문 사용이 제각각이었습니다.

## 4. 제안서의 한계에 대한 대응

| 제안서의 한계            | 새 설계의 대응                              | 해결 정도          |
| ------------------ | ------------------------------------- | -------------- |
| 1. 목표와 실제 길이 차이    | 길이 지시를 없애고 실제 길이를 측정해 보고              | 차이를 인정하고 보고    |
| 2. 질문 사용 여부 차이     | 메인은 질문 없이, 질문은 추가 분석 1에서 따로           | 구조적으로 해결       |
| 3. 조건·예외 손실, 문장 변형 | 추출형 조건, 보존 우선 지시, Gold Evidence 오류 분석 | 크게 완화          |
| 4. 계산 비용과 일반화      | 질문별 압축을 추가 분석으로 한정                    | 일반화 한계는 그대로 남음 |

LongLLMLingua가 새 설계에서 빠진 이유는 문서에 명시되어 있지 않습니다. 질문을 쓰면서 토큰을 삭제하는 방식이라 여러 변인을 섞는다는 추정이 있으나 확인된 사실은 아닙니다.

## 5. 예시 (설명용으로 만든 가상의 예시이며 실제 데이터가 아닙니다)

- 계약서 문장: "수령자는 기밀정보를 공개하지 않는다. 단, 법원이 요구하는 경우는 예외로 한다."
- 가설: "수령자는 법원의 요구가 있으면 기밀정보를 공개할 수 있다." (정답: Entailment)

**기존 설계에서**

- Naive 요약이 "수령자는 기밀정보를 공개하지 않는다."로 줄이면 예외가 사라져 Contradiction이라고 답할 수 있습니다.
- LongLLMLingua가 이 문장을 잘 살렸더라도, 질문을 알았기 때문인지 알고리즘이 좋아서인지 구분할 수 없습니다.

**새 설계에서**

- 생성형·일반과 생성형·보존 우선은 "예외를 우선하라"는 문장 하나만 다르므로 그 지시의 효과만 볼 수 있습니다.
- 추출형은 문장을 고르면 "단, … 예외로 한다"가 원문 그대로 함께 남습니다. 다만 그 문장을 아예 고르지 않을 수는 있습니다.
- 질문의 효과는 같은 조건에 가설만 추가해 따로 측정합니다.

## 6. 남는 한계와 주의점

- 일반화 한계(ContractNLI 하나, 모델 두 개, 17개 고정 가설)는 설계를 바꿔도 해결되지 않습니다.
- 메인에서 길이를 통제하지 않으므로 조건 간 성능 차이에 길이 차이가 섞일 수 있습니다. 추가 분석 2에서 다룹니다.
- 의미 보존의 정량화는 기본 계획에 없습니다. 사람 검토 기준을 따로 정해야 하며 필수 게이트도 아닙니다.
- 추출형은 문장 내용은 보존하지만 중요한 문장을 고르지 않으면 정보가 사라집니다. 손실 위치가 "문장 변형"에서 "문장 누락"으로 바뀝니다.
