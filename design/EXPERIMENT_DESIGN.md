# 계약서 문맥 압축 실험 설계

작성일: 2026-11-12

상태: 메인 5조건의 실행 코드를 새로 구현했다. 추가 분석은 구현하지 않았다. 프롬프트 전문과 구현 기본값은 코드 및 docs/DECISIONS.md에 기록하고, 사용자의 새로운 Dev 기술 점검을 거쳐 Test 전에 동결한다. 실제 모델·Dev/Test 실험 결과는 아직 없다.

**이번 작업의 범위**

이전 실험의 압축문, 예측, 성능 수치, 전처리 검토 결과, 제외 ID 목록을 재사용하지 않는다. 공식 데이터부터 다시 점검하고 Original도 새로 평가한다. 기존 실행 폴더와 결과를 덮어쓰지 않는다.

코드는 사용자의 작성 요청에 따라 새로 구성했다. 모델 다운로드·로딩·Dev/Test 실험은 사용자가 로컬에서 진행한다. 에이전트의 검증은 작은 CPU 테스트, 구문·입출력·CLI 점검 등으로 제한한다.

**연구 목적**

질문을 미리 알려주면 계약 판단에 필요한 정보를 더 잘 보존할 수 있는지 확인한다. 이를 위해 먼저 질문 없는 압축의 기본 성능을 비교하고, 질문 제공, 길이 제약, Gold Evidence 기반 오류 분석을 추가한다.

질문 정보는 ContractNLI에서 판단할 가설 문장이다. 질문 제공 효과의 직접적인 검증은 추가 분석 1에서 수행한다.

**데이터와 모델**

| 항목 | 원칙 |
|---|---|
| 데이터 | ContractNLI 공식 Train/Dev/Test 분할 |
| Train | 학습과 모델 추론에 사용하지 않고 교차 중복 점검에만 사용 |
| Dev | 전처리·출력 형식·파싱·실행 가능성 등 기술 점검에 사용 |
| Test | 새 전처리 목록과 확정한 메인 규칙으로 평가 |
| 압축·선택 모델 | Qwen2.5-7B-Instruct, 네 압축 조건이 같은 모델과 정밀도 사용 |
| 판단 모델 | Qwen3-8B, thinking off, 전 조건 같은 판단 설정 |
| 정밀도 | 두 모델의 4bit 공통 설정을 고정하고 실제 설정 기록 |
| 디코딩 | Greedy, 고정한 공통 설정 사용 |
| 학습 | 별도 학습·미세조정 없음 |

공식 데이터는 Train 423, Dev 61, Test 123문서와 고정 17개 가설로 구성된다. 실제 평가 문서 수는 새 검토와 제외 목록에서 계산하며 이전 실험의 최종 수를 가져오지 않는다.

참고: https://stanfordnlp.github.io/contract-nli/

**새 전처리**

1. 공식 원본 파일을 확보하고 파일 해시·획득 정보를 기록한다. 원본 계약서, 라벨, Gold Evidence의 문자 위치는 보존한다.
2. 문서 ID, 가설 목록, 17개 라벨, 허용 라벨 값, 원문과 span 범위, 근거 인덱스 등을 검사한다. 데이터 문제를 자동으로 덮어쓰지 않고 기록한다.
3. 중복 탐지용 정규화 사본을 별도로 만든다. 정규화 규칙을 기록하며, 이를 모델 입력 원문으로 자동 대체하지 않는다.
4. 원문 완전 중복, 정규화 중복, 유사 중복 후보를 새로 생성한다. 유사도 방식과 후보 임계값은 구현 명세에 기록하고, 유사도만으로 자동 제외하지 않는다.
5. 사람이 같은 계약서로 확인한 그룹에서 라벨도 일치하면 가장 작은 ID 하나를 유지한다. 실질적으로 같은 내용인데 라벨이 충돌한다고 확인된 그룹은 임의 재라벨링하지 않고 전체 제외한다. 단순히 유사도가 높고 라벨이 다르다는 이유만으로 제외하지 않는다.
6. Evidence 위치나 표현의 차이는 라벨 충돌과 구분해 기록한다. Dev/Test 교차 중복에서 같은 계약서로 확인되면 Test를 유지하고 Dev 개발 대상에서 제외한다. Train과의 중복은 별도로 보고한다.
7. 최종 제외 목록에 ID, 관련 ID, 처리 유형, 사유와 검토 내용을 기록한다. 공식 파일을 수정하는 대신 실행 대상 목록으로 적용한다.

이 목록과 최종 평가 문서 수는 실제 데이터 점검 이후 확정할 산출물이다. 과거 제외 목록으로 미리 채우지 않는다.

**추출 단위**

공식 문서의 전체 `spans`를 우선적인 선택 단위로 검토한다. 각 span은 원문의 문장 또는 목록 항목에 해당하는 문자 위치 정보다. 새 데이터에서 범위가 유효한지, 분할로 원문 내용이 빠지는지, 비정상적으로 분리된 구간이 있는지 검사한 뒤 사용 규칙을 확정한다. 필요한 보완이 있으면 일관된 규칙과 원문 위치 대응을 기록한다.

문서의 전체 span 목록과 가설별 Gold Evidence 목록은 구분한다. 압축에는 모든 후보 단위의 ID·본문만 제공하고, 어느 단위가 Gold Evidence인지는 제공하지 않는다. 모든 압축 조건에는 동일한 번호가 붙은 원문을 제공한다.

ID는 원문 단위의 식별자이며 중요도 등수가 아니다. 모델에는 선택한 ID 목록을 반환하도록 하고 중요도순 반환은 요구하지 않는다. 최종 추출 문맥은 원문 위치 순으로 정렬해 병합한다. 선택 단위 내부는 자르거나 다시 쓰지 않는다.

**메인 실험: Original과 압축 4조건**

| 조건 | 출력 방식 | 보존 우선순위 지시 | 압축 시 질문 |
|---|---|---|---|
| Original | 원문 그대로 | 해당 없음 | 해당 없음 |
| 생성형·일반(Naive) | 축약 본문 작성 | 없음 | 없음 |
| 생성형·보존 우선(Contextualized) | 축약 본문 작성 | 있음 | 없음 |
| 추출형·일반 | 원문 단위 ID 선택 | 없음 | 없음 |
| 추출형·보존 우선 | 원문 단위 ID 선택 | 있음 | 없음 |

보존 우선순위는 의무 주체, 조건, 예외, 부정·금지, 논리 연결, 적용 범위다. 두 보존 우선 조건에 같은 문장을 사용한다. 같은 압축 방식 안에서는 이 문장 하나만 다르게 하고 나머지 지시와 설정은 유지한다.

공통 지시는 원문을 데이터로 취급하고, 원문에 없는 내용을 추가하지 않으며, 사실적 의미를 보존하도록 한다. 프롬프트 전문은 contract_experiment/prompts.py에서 확인하며, Dev 기술 점검 후 Test 전에 동결한다.

메인에서는 출력 분량을 지정하는 추가 지시를 사용하지 않는다. 목표 토큰 수·보존율·문장 수·선택 개수·남은 예산 등을 프롬프트에 넣지 않는다. 최소 길이 강제, 목표 길이에 맞춘 재작성·후보 선택·추가 생성도 하지 않는다.

실행을 위한 안전 상한과 정지 문자열은 Dev에서 기술적으로 점검한다. 안전 상한은 목표 보존율이 아니며 도달 여부를 기록한다. 상한 도달만으로 의미적 미완성을 확정하지 않는다.

판단 모델에는 모든 조건에서 같은 형식으로 문맥과 가설을 제공한다. 압축 모델에 가설을 숨기는 것과 판단 모델에 가설을 제공하는 것은 별개의 단계다.

**메인의 출력 처리 방향**

| 상황 | 합의한 추천 방향 |
|---|---|
| 유효한 선택 ID 목록 | 원문 위치 순서로 정렬해 원문 단위를 병합 |
| 중복 ID | 한 번만 사용하고 중복 발생 기록 |
| 정상적인 빈 목록 `[]` | 빈 선택으로 기록하고 빈 문맥으로 판단 |
| 존재하지 않는 ID 또는 해석 불가능한 형식 | 압축 실패로 기록. 원문 대체·자동 재생성하지 않음 |
| 판단 라벨 추출 실패 | 원본 보존, 오답 처리, 실패율 보고 |

허용할 JSON 포장 형식, 압축 실패 행의 구체적인 집계 표현 등 구현 세부는 메인 Dev 전에 명시하고 Test 전에 고정한다. 실패 행을 조용히 제거하지 않는다.

**추가 분석 1: 질문 제공 효과**

네 압축 조건 각각에서 계약서만 제공한 경우와 계약서에 가설 한 개를 추가한 경우를 비교한다. 가설 입력 이외의 작업 지시·모델·정밀도·디코딩·출력 형식은 유지한다. 가설은 검증 대상이며 참으로 가정하지 않도록 공통 규칙을 둔다.

길이 지시는 사용하지 않는다. 질문 없는 문맥은 문서당 하나를 여러 가설에 재사용하지만, 질문 있는 문맥은 문서·가설별로 생성한다. 성능 변화에는 출력 길이 변화도 포함될 수 있으므로 길이와 비용을 함께 보고한다.

**추가 분석 2: 코드로 적용한 길이 제약**

메인 이후 준비해도 된다. 목표 보존율, 허용오차, 예산에 맞춘 추출 조합은 메인 실행의 선행 조건이 아니다. 목표 보존율은 아직 정하지 않았으며, 허용오차는 이 분석의 길이 제어를 Dev에 실제 적용한 뒤 결정한다. 특정 예시 비율을 기본값으로 넣지 않는다.

이 단계에서도 프롬프트에는 길이 통제 지시를 넣지 않는다. 문서별 예산은 코드에서 계산한다. 질문 없음과 있음에 같은 원문 기준 예산 및 처리 규칙을 적용한다.

생성형은 코드의 최소·최대 생성 길이 제어를 검토한다. 추출형은 문장·조항 전체를 유지하며 예산에 맞춘 선택 절차를 사용한다. 조합 및 실패 처리 세부는 이 분석을 준비할 때 결정한다. 허용 범위는 Dev에서 정하고 네 조건에 공통 적용한다. 개별 Test 문서에 맞춰 범위를 계속 넓히지 않는다.

반복·원문 불일치·상한 종료·범위 이탈도 결과로 기록한다. 같은 허용 구간이라는 사실을 실제 길이의 정확한 일치로 해석하지 않는다. 추출형의 선택 절차가 메인과 달라지면 그 차이도 명시한다.

**추가 분석 3: Gold Evidence 기반 오류 분석**

질문 제공 및 길이 제약 전후의 개선·악화·지속 오답 사례를 원문 근거와 대조한다. 근거 누락, 주체·조건·예외·부정 등의 의미 변경, 원문에 없는 내용, 출력 잘림, 판단 오류 후보를 살펴본다.

단어 일치와 의미 보존을 구분한다. 근거 누락만으로 길이 상한이 원인이라고 단정하지 않고 종료 상태·문장·선택 로그를 함께 확인한다. NotMentioned는 Gold Evidence가 없으므로 근거 보존율 분모에 넣지 않는다.

기본은 오류 사례 분석이다. 의미적 보존율이나 오류율을 수치화하려면 검토 표본과 판정 기준을 별도로 정하고 검토 범위에 맞게 해석한다. 사람 검토를 메인 실행의 필수 게이트로 만들지 않는다.

Lost in the Middle 및 중요도순 재배열 분석은 포함하지 않는다.

**평가와 기록**

주요 성능은 Accuracy와 Macro-F1이며 혼동행렬·클래스 Recall·파싱 실패율을 함께 보고한다. Original 대비 정확도 차이와 정답 유지율도 확인한다. 같은 문서의 17문항을 묶어 차이의 불확실성을 계산한다.

실제 보존율은 최종 판단 문맥의 Qwen3 토큰 수를 원문 문맥의 Qwen3 토큰 수로 나눈 값이다. 지시문·가설·채팅 형식·단위 ID 표시는 제외한다. 추출형은 조합된 원문을 측정한다.

압축·판단 시간, 원본 출력, 선택 ID와 원문 위치, 실패와 종료 상태, 실제 입력 및 출력 토큰 수를 남긴다. 프롬프트 전문·해시, 데이터·제외 목록 해시, 모델 리비전, 정밀도, 라이브러리, 템플릿과 생성 설정도 기록한다.

**진행 순서**

합의한 메인 규칙 명세 → 사용자 요청 후 새 코드 작성 → 최소 CPU 검증 → 사용자의 새 데이터 전처리 및 Dev 실행 → 기술 문제 수정과 설정 기록 → 새 Original 및 메인 4조건 실행 → 이후 추가 분석 준비.

추가 분석 2의 수치를 정하기 위해 메인 진행을 보류하지 않는다. 데이터 제외 목록과 안전 상한의 적절성은 실제 데이터 및 Dev 점검을 통해 확정한다. Dev 판단 정확도를 높이는 방향으로 규칙을 선택하지 않는다.
