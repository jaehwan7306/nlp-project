## 연구 질문

**평가할 가설을 압축 전에 알려 주면, 판단에 필요한 계약서 정보를 더 잘 남길 수 있는가?** Main과 Analysis 1은 압축 문맥으로 같은 가설을 얼마나 정확하게 판단하는지 측정했다. 후속 분석에서는 입력에서 근거가 놓인 위치와 압축 후 근거가 남는 양상을 각각 살펴볼 예정이다.

## 데이터 준비와 공통 설정

ContractNLI는 계약서가 주어진 가설을 뒷받침하는지(Entailment), 반박하는지(Contradiction), 어느 쪽도 확정할 수 없는지(NotMentioned)를 판별하는 데이터셋이다. 공식 분할은 Train 423, Dev 61, Test 123문서다. 이 프로젝트의 최종 Test는 중복·라벨 충돌 검토를 거친 **119문서 × 17가설 = 2,023문항**이다. [ContractNLI 논문](https://aclanthology.org/2021.findings-emnlp.164/) · [제외 결정](../docs/RESULTS.md#데이터와-실행-범위)

1. 공식 원본의 해시, 문서·가설 ID, 주석과 문자 범위를 점검한다. 중복 검색에는 정규화 사본을 사용하며 모델에는 원문 내용을 전달한다.
2. 사람 검토로 쌍마다 `duplicate`, `exclude_both`, `distinct`를 기록한다. `duplicate`는 Test를 우선하고 같은 분할에서는 작은 ID를 유지한다. 나머지 두 선택지는 각각 양쪽 제외와 별개 문서 유지를 뜻한다. 최종 제외 사유와 ID를 보관한다.
3. Train은 교차 중복 감사에 사용한다. Dev는 입력·출력 형식과 실행 가능성을 점검하는 데 쓰고, Test 전에 프롬프트·모델·실행 설정을 동결한다. 학습과 미세조정 없이 평가한다.

| 항목 | 실행 설정 |
|---|---|
| 압축·선택 | Qwen2.5-7B-Instruct |
| 판단 | Qwen3-8B, thinking off |
| 정밀도·디코딩 | 두 모델 모두 4bit NF4, bfloat16, 명시적 greedy |
| 긴 입력 | 전체 문맥을 유지하며 긴 prefill의 attention을 head별로 계산 |
| 출력 길이 | 자연 생성 길이를 측정하고, 공통 안전 상한과 종료 상태를 기록 |

긴 입력의 메모리 보완 정책을 Main Test의 첫 생성부터 전 조건에 적용했다. Analysis 1도 같은 정책과 모델 설정을 사용했다. 실행마다 설정·실제 runtime·프롬프트·소스 해시를 보관하고 중단 후 같은 조건으로 이어 간다. [구현과 검증](../docs/IMPLEMENTATION.md) · [고정 모델 리비전](../docs/model_revisions.json)

## Main · Original과 질문 없는 압축

| 조건 | 사용할 문맥 | 보존 우선 지시 |
|---|---|---|
| Original | 계약서 원문 | 해당 없음 |
| Naive | 새로 쓴 요약문 | 일반 지시 |
| Contextualized | 새로 쓴 요약문 | 보존 우선 |
| 추출형·일반 | 선택한 원문 단위의 조합 | 일반 지시 |
| 추출형·보존 우선 | 선택한 원문 단위의 조합 | 보존 우선 |

네 압축 조건에 같은 번호가 붙은 계약서를 제공한다. 원문 단위는 공식 `spans`를 바탕으로 만들고, 필요한 구간을 보완해 원문 문자 범위를 기록한다. 추출형은 선택한 ID에 해당하는 단위를 통째로 원문 순서대로 연결한다. 보존 우선 조건에는 의무 주체, 조건과 예외, 부정과 금지, 논리 연결, 적용 범위를 우선하라는 같은 문장 하나를 추가한다. [Main 프롬프트](../contract_experiment/prompts.py)

판단에는 원문 또는 압축 문맥과 현재 평가할 가설 한 개를 제공한다. 압축 ID의 중복은 한 번만 반영하고 빈 선택 `[]`은 빈 문맥으로 평가한다. 형식이나 ID 오류로 압축이 실패한 문항과 판단 라벨 파싱에 실패한 문항은 오답으로 기록한다. [Main 상세 결과](../docs/RESULTS.md#main-질문-없는-압축)

## Analysis 1 · 가설 제공 효과

네 압축 방법에서 **압축기에 보여주는 가설 수**를 바꾼다. 문서·방법마다 압축문을 하나 만들고 그 문맥으로 가설 17개를 각각 판단한다. Original 문맥과 판단 기록은 Main에서 재사용한다.

| 조건 | 압축 입력에 추가한 가설 |
|---|---|
| Q0 | 0개. Main의 질문 없는 압축 |
| Q8 | 계약서마다 배정한 8개 |
| Q17 | 공식 17개 전체 |

Q8은 문서와 가설 ID만 사용해 seed 42로 배정한다. 각 가설은 119개 계약서 중 56개에서 제공되고 63개에서 빠진다. 같은 계약서의 네 방법에는 같은 목록을 사용하고, 남은 가설의 원래 번호와 상대적 순서를 유지한다. Q8과 Q17에 공통으로 가설이 검증할 주장이라는 안내를 넣는다. 정답 라벨과 근거 주석은 모델 입력과 별도로 보관한다. [Q17 프롬프트](../question_support/prompts.py) · [Q8 배정 구현](../question_subset/assignment.py)

전체 2,023문항에서 같은 문서·가설의 예측을 비교한다. 보조 분석에서는 Q8이 보여준 **952문항**과 빠진 **1,071문항**을 Q0·Q8·Q17에 같은 기준으로 적용한다. 각 묶음 안에서 정확도 변화량을 비교하면, 질문 자체의 기본 난도 차이를 줄일 수 있다. [Q8 결과](../results/questions8/report.md) · [실행 순서](../docs/REPRODUCIBILITY.md#questions8)

## Analysis 2 · Lost in the Middle

**예정. 모델이 읽는 실제 입력에서 판단 근거가 앞, 중간, 뒤에 놓일 때 정답률이 어떻게 달라지는지 살핀다.** 선행연구는 관련 정보를 긴 입력의 여러 위치에 옮겨 성능 변화를 시험했다. 이번 계획은 ContractNLI의 실제 입력 순서에서 근거 위치별 판단 성능을 관찰하는 데서 시작한다. [Liu et al., 2024](https://aclanthology.org/2024.tacl-1.9/)

| 모델이 읽는 단계 | 입력 순서 |
|---|---|
| 압축 | 지시 → 제공 가설 목록(Q8·Q17) → 번호가 붙은 계약서 원문 |
| 판단 | 분류 지시 → 원문 또는 압축 문맥 → 현재 평가할 가설 1개 |

Gold Evidence는 어떤 가설의 판단 근거가 되는지 표시한 **원문의 문자 범위**다. 가설별 근거 ID를 문서의 `spans`에 연결하면 범위를 찾을 수 있다. 문장이나 조항은 일반 계약서 내용으로 입력되고, 근거 주석은 저장된 문항을 분석할 때 연결한다. 프롬프트 지시와 가설이 추가되면 전체 입력에서 같은 문장의 토큰 위치도 달라질 수 있다. [공식 데이터 형식](https://stanfordnlp.github.io/contract-nli/) · [판단 프롬프트](../contract_experiment/prompts.py)

1. 원문이 그대로 들어가는 Original 판단 입력부터 재구성해 근거의 위치를 확인한다. 계약서 구간 내 위치와 지시·가설을 포함한 전체 입력 내 위치를 각각 기록한다.
2. 근거가 여러 곳에 흩어진 문항의 처리와 앞·중간·뒤 구간 경계를 먼저 정한다. 근거 위치가 없는 문항은 별도 집계한다.
3. 구간별 문항 수와 정답률을 비교한다. 계약서 길이와 가설·라벨 분포의 차이를 함께 보고하고, 관찰된 차이는 위치와 성능의 관계로 해석한다.

## Analysis 3 · Gold Evidence 보존과 오류

**예정. 같은 문항의 판단 결과가 바뀌었을 때, 원문에서 답의 근거가 된 내용이 압축 문맥에 어떻게 남았는지 살핀다.** Q0·Q8·Q17에서 오답이 정답으로, 정답이 오답으로 바뀐 사례와 계속 틀린 사례를 원문 근거와 대조한다. [ContractNLI의 근거 주석](https://aclanthology.org/2021.findings-emnlp.164/)

- **추출형**은 남긴 단위의 ID와 문자 범위로 어떤 근거가 포함됐는지 추적한다.
- **생성형**은 표현이 바뀌어도 의무, 기한, 조건, 예외 같은 핵심 의미가 유지됐는지 확인한다.
- **오류 유형**으로 근거 누락, 의미 변경, 원문에 없는 진술 추가, 출력 상한에서의 종료, 근거가 남았는데도 발생한 오판을 기록한다.

사례 선정과 의미 보존 판정 기준은 실행 전에 정한다. 근거 보존율을 계산할 경우 근거 주석이 있는 문항을 대상으로 계산하고 분모를 명시한다. Analysis 2는 **입력에서 근거가 놓인 위치**를, Analysis 3은 **근거가 압축 문맥에 어떻게 남았는지**를 살핀다.

## 평가 지표와 해석

- **성능**은 정확도, Macro-F1, 라벨별 Recall과 실패율로 보고한다. 비교의 95% 신뢰구간은 같은 계약서의 문항을 묶어 10,000회 복원추출해 계산한다. Seed는 42다.
- **실제 토큰 보존율**은 최종 판단 문맥의 Qwen3 토큰 수를 원문 토큰 수로 나눈 값이다. 자유 생성 길이를 사용했으므로 방법이나 가설 제공 조건 사이의 성능 차이에는 실제 길이와 출력 형식의 영향도 포함될 수 있다.
- **재현 기록**에는 원문·문맥과 예측, 모델과 프롬프트, 입력·출력 길이, 종료와 실패, 추출 범위, 압축·판단 시간을 보관한다.
