## 연구 질문

**평가할 가설을 압축 전에 알려 주면, 판단에 필요한 계약서 정보를 더 잘 남길 수 있는가?** Main은 질문을 전혀 주지 않은 Q0와 17개 모두 준 Q17을 비교한다. Analysis 1은 가설 8개를 준 Q8을 두 조건과 비교한다. 후속 분석은 입력에서 근거가 놓인 위치와 압축 후 근거가 남는 양상을 살핀다.

## 데이터 준비와 공통 설정

ContractNLI는 계약서가 주어진 가설을 뒷받침하는지(Entailment), 반박하는지(Contradiction), 어느 쪽도 확정할 수 없는지(NotMentioned)를 판별하는 데이터셋이다. 공식 분할은 Train 423, Dev 61, Test 123문서다. 이 프로젝트의 최종 Test는 중복·라벨 충돌 검토를 거친 **119문서 × 17가설 = 2,023문항**이다. [ContractNLI 논문](https://aclanthology.org/2021.findings-emnlp.164/) · [제외 결정](02_main_q0_vs_q17.md#데이터와-실행-범위)

1. 공식 원본의 해시, 문서·가설 ID, 주석과 문자 범위를 점검한다. 중복 검색에는 정규화 사본을 사용하며 모델에는 원문 내용을 전달한다.
2. 사람 검토로 쌍마다 `duplicate`, `exclude_both`, `distinct`를 기록한다. `duplicate`는 Test를 우선하고 같은 분할에서는 작은 ID를 유지한다. 나머지 두 선택지는 각각 양쪽 제외와 별개 문서 유지를 뜻한다. 최종 제외 사유와 ID를 보관한다.
3. Train은 교차 중복 감사에 사용한다. Dev는 입력·출력 형식과 실행 가능성을 점검하는 데 쓰고, Test 전에 프롬프트·모델·실행 설정을 동결한다. 학습과 미세조정 없이 평가한다.

| 항목 | 실행 설정 |
|---|---|
| 압축·선택 | Qwen2.5-7B-Instruct |
| 판단 | Qwen3-8B, thinking off |
| 정밀도·디코딩 | 두 모델 모두 4bit NF4, bfloat16, 명시적 greedy |
| 긴 입력 | 전체 문맥을 유지하며 긴 prefill의 attention을 head별로 계산 |
| 출력 길이 | 자연 생성 길이를 측정하고, 공통 안전 상한과 종료 상태를 기록 |

긴 입력의 메모리 보완 정책을 Original·Q0의 첫 Test 생성부터 적용했고 Q17과 Q8에도 같은 정책과 모델 설정을 썼다. 실행마다 설정·실제 runtime·프롬프트·소스 해시를 보관하고 중단 후 같은 조건으로 이어 간다. [구현과 검증](implementation.md) · [고정 모델 리비전](model_revisions.json)

## Main · 질문 유무 비교

메인의 주 비교는 **Q17−Q0**다. Q0에서는 압축기에 원문만 주고, Q17에서는 같은 원문에 공식 가설 17개를 모두 붙인다. 아래 네 압축 방법을 두 조건에 각각 적용한다. 계약서 원문을 그대로 읽는 Original로 기준 성능을 확인한다.

| 조건 | 사용할 문맥 | 보존 우선 지시 |
|---|---|---|
| Original | 계약서 원문 | 해당 없음 |
| Naive | 새로 쓴 요약문 | 일반 지시 |
| Contextualized | 새로 쓴 요약문 | 보존 우선 |
| 추출형·일반 | 선택한 원문 단위의 조합 | 일반 지시 |
| 추출형·보존 우선 | 선택한 원문 단위의 조합 | 보존 우선 |

네 압축 조건에 같은 번호가 붙은 계약서를 제공한다. 원문 단위는 공식 `spans`를 바탕으로 만들고, 필요한 구간을 보완해 원문 문자 범위를 기록한다. 추출형은 선택한 ID에 해당하는 단위를 통째로 원문 순서대로 연결한다. 보존 우선 조건에는 의무 주체, 조건과 예외, 부정과 금지, 논리 연결, 적용 범위를 우선하라는 같은 문장 하나를 추가한다. [Main 프롬프트](../contract_experiment/prompts.py)

Q0와 Q17 모두 문서·방법마다 압축문 하나를 만들고, 그 문맥으로 **같은 17개 가설을 하나씩 판단**한다. Q17에는 가설 목록을 검증할 주장으로 읽으라는 안내가 추가된다. 정답 라벨과 근거 주석은 평가 자료에 보관한다. Original의 문맥과 예측은 한 번 평가해 재사용한다. [기본 프롬프트](../contract_experiment/prompts.py) · [Q17 질문 목록](../question_support/prompts.py)

압축 ID의 중복은 한 번만 반영하고 빈 선택 `[]`은 빈 문맥으로 평가한다. 형식이나 ID 오류로 압축이 실패한 문항과 판단 라벨 파싱에 실패한 문항은 오답으로 기록한다. [메인 실험 상세 결과](02_main_q0_vs_q17.md)

## Analysis 1 · 가설을 8개만 제공

Q8은 압축기에 계약서별 가설 목록 8개를 주고 문서·방법별로 한 번 압축한다. 모든 문서에서 같은 17개 가설을 하나씩 판단한다. 메인 실험의 Q0·Q17과 Original은 완료한 결과를 재사용한다.

Q8은 문서와 가설 ID만 사용해 seed 42로 배정한다. 각 가설은 119개 계약서 중 56개에서 제공되고 63개에서 빠진다. 같은 계약서의 네 방법에 같은 목록을 쓰고, Q17과 동일한 안내 및 가설의 원래 번호·상대 순서를 사용한다. [Q8 배정 구현](../question_subset/assignment.py)

전체 2,023문항에서 같은 문서·가설의 예측을 비교한다. 보조 분석에서는 Q8이 보여준 **952문항**과 빠진 **1,071문항**을 Q0·Q8·Q17에 같은 기준으로 적용한다. 각 묶음 안에서 정확도 변화량을 비교하면, 질문 자체의 기본 난도 차이를 줄일 수 있다. [Q8 결과](03_analysis1_q8.md) · [실행 순서](reproducibility.md#questions8)

## Analysis 2·3 · 결과의 원인 분석

메인 실험과 분석 1에서 나타난 차이의 원인을 두 방향에서 확인한다.

- **[Analysis 2 · 근거 위치](04_analysis2_position.md):** 모델이 읽는 실제 입력에서 근거가 앞·중간·뒤 중 어디에 놓이느냐에 따라 정답률이 달라지는가.
- **[Analysis 3 · Gold Evidence 보존](05_analysis3_evidence.md):** 판단이 바뀐 문항에서 원문의 근거가 압축 문맥에 어떻게 남아 있었는가.

## 평가 지표와 해석

- **성능**은 정확도, Macro-F1, 라벨별 Recall과 실패율로 보고한다. 비교의 95% 신뢰구간은 같은 계약서의 문항을 묶어 10,000회 복원추출해 계산한다. Seed는 42다.
- **실제 토큰 보존율**은 최종 판단 문맥의 Qwen3 토큰 수를 원문 토큰 수로 나눈 값이다. 자유 생성 길이를 사용했으므로 방법이나 가설 제공 조건 사이의 성능 차이에는 실제 길이와 출력 형식의 영향도 포함될 수 있다.
- **재현 기록**에는 원문·문맥과 예측, 모델과 프롬프트, 입력·출력 길이, 종료와 실패, 추출 범위, 압축·판단 시간을 보관한다.


설계 결정의 근거는 [개발 기록](dev-log/README.md)에 있다.
